# v0.6.0 development progress

This is an implementation-start record, not a completion or release record.
The starting implementation is `4596dc4dc28fa8bc1c1b73eb3debb19e9fee95bb`.

## Implemented increment

- String literal scanning, decoded UTF-8 payloads, postfix method AST nodes,
  string types, and typed operation records.
- Independent CheckedProgram validation of operation kind, ordered operands,
  signature, result, and early-exit summaries.
- Host text objects, scalar length/slicing, content equality, copy concatenation,
  and ordered Common Lisp forms with caller control-flow targets.
- Shared runtime failure base, retained integer subtype, prebuilt diagnostics,
  and separately classified program/compilation storage failures.

## Validation and reproduction

Run `sbcl --noinform --script scripts/test.lisp` and `git diff --check`.
The pre-change baseline passed 94 groups, 12,933 assertions, and 1,141 child
processes. This increment adds ten groups. Three historical groups containing the newly
reserved identifier `string` have explicit migrated replacements; their original
fixture file remains unchanged. The replacement retains every unrelated case.
Exact reviewed commits, commands, and final suite results are recorded in the
pull request; the content manifest identifies the delivered files.

The host GC child can also be run directly:

```sh
sbcl --dynamic-space-size 256 --noinform --script tests/v06-host-gc-entry.lisp
```

On SBCL 2.6.0.debian / ASDF 3.3.1, the 256 MiB child allocated 1,179,779,072
payload bytes in 9,001 allocations. All 9,001 weak references were dead after
full GC, and the separately held three-byte value retained its contents.
Observed resident dynamic usage after compilation was 33,180,896 bytes.
The test asserts measured allocation and weak-reference outcomes; collection
counts alone are not used as proof. Test-only wrappers hold no strong references
to the dynamic results.

Static negative tests exercise both run and build, including existing output
preservation. Successful text execution, scalar-oracle comparisons, injected
runtime failures, and text reclamation currently exercise the host backend only.
All successful host samples finish with the existing boolean output contract.

## Remaining work

Core text operations and deterministic literal pooling, independent root
analysis/verification, ABI v3 and root frames, native text helpers and
mark-and-sweep, native finite-heap evidence and failure injection, cross-backend
acceptance, and text artifact regression remain unimplemented/unverified.
The existing native backend may reject otherwise valid text programs as an
internal unsupported-node/signature failure. This intermediate development
snapshot must not be treated as native text support or a v0.6.0 release.

## Diagnostic failure follow-up

The double-failure child reproduces an allocation failure followed by a
storage condition while writing its runtime diagnostic. Diagnostic handlers now
catch that condition explicitly: runtime failure retains exit 4, and failed
compiler/source diagnostic delivery returns exit 3. The child checks empty
output and marks any execution of the subsequent arithmetic with exit 99.
A separate concat test isolates scalar-count overflow after the byte-size check
and before payload allocation, without constructing a huge payload.
